# 设计理念

ezloop 是一个用 Go 写的 Agent 循环引擎。它解决的问题是：**当你把模型、工具、重试、审批、会话持久化这些能力组合成一个 agent 时，组合逻辑放在哪里。**

常见的做法是把它们做进框架：框架内置 MCP、内置审批、内置会话管理。短期省事，长期的问题是引擎越来越重——每个能力的升级都牵动引擎，没用某个能力的项目也要背上它的代码和依赖。

ezloop 的答案是把引擎缩小到只剩不可省略的部分，其余全部外挂。

## 引擎只保留三件事

1. **循环**：驱动「模型 → 工具 → 模型」，直到模型不再发起工具调用、达到迭代上限、被钩子终止或出错。
2. **历史**：消息序列（`LoopState.Messages`）在任何退出路径下保持协议完整——每个 tool_call 必有对应的工具结果消息。它是唯一的状态载体，可序列化、可存盘、下一轮直接作为历史传入。
3. **事件**：执行过程以事件流实时透出（流式增量、工具起止、迭代边界），事件只做观察，不用于改状态。

这三件事之外没有别的「引擎能力」。

## 双层扩展模型

能力外挂分两层，按「管什么」划分：

| 层 | 管什么 | 形态 | 例子 |
| --- | --- | --- | --- |
| **warp（装饰器）** | 节点**怎么执行** | 包住节点内部的中间件 | 重试、限流、panic 防护 |
| **hook（钩子）** | 流程**什么时候**插入逻辑 | 挂在节点外部的时机点 | 审批拦截、上下文压缩、会话保存 |

判断一个新能力放哪层：如果它关心单次模型调用或单次工具执行的执行方式，是 warp；如果它关心循环流程中的某个时机（开始前、工具调用前、每轮回边、结束），是 hook。

两层平级，不互相调用：warp 拿到的只有事件出口（发观察事件），碰不到 state；hook 拿到完整 `LoopState`。

## 三条不变量

**所有能力都是扩展。** 引擎代码不 import 任何扩展包。重试是 warp，MCP、审批、会话保存都是 hook——不用不引入，升级互不影响。

**状态即消息。** 循环的全部状态是 `LoopState.Messages`，没有隐藏的内存中间态。多轮对话就是把上一轮的 Messages 用 `WithHistory` 传回来；会话恢复就是从盘上读出 Messages 再传回来。引擎不做断点续传——恢复即新对话，模型看历史自己决定下一步。

**Agent 构建后只读。** `NewAgent` 返回后 Agent 不可变。这是一个框架契约，换来两个性质：可以做成全局单例被多个 goroutine 并发 `Run`（服务端多租户的基础）；Fork 派生分身只需要浅拷贝，不需要理解组装过程。

## 依赖方向

```
框架层（零第三方依赖）
types / event / hook / provider / warp / core
        ↑
扩展层（第三方依赖只出现在这里）
ext/provider/openai、ext/warp/*、ext/hook/*
```

core 永不 import ext。官方扩展和第三方扩展地位相同——如果你写了一个自己的重试 warp，它和 `modelretry` 是完全对等的。

## 静态说明的声明式通道

工具的使用说明（给模型看的 `<tool-guide>` 之类文本）本质是静态数据，早期版本由各 hook 在 OnStart 里手动拼进 system 消息——这带来两个隐患：拼装顺序依赖注册顺序（重写 system 的 hook 必须排在前面），以及拼装逻辑分散在各个 hook 里难以审视。

现在这类内容走 `GuideHook` 声明：hook 实现 `Guide() string` 返回静态文本，引擎在组装期统一收集、按注册序追加。顺序与幂等由引擎保证，静态贡献成为不跑循环也能枚举的数据。每轮变化的内容（身份、状态快照）仍然用 StartHook。

## 为什么没有更多的钩子点

曾经考虑过「构建期钩子」（hook 在 NewAgent 时拿到 Agent 引用做一次性初始化），最终否决：构建期定制一律走 Option，运行期行为走 hook，出现第三态会让分层变模糊，浅拷贝 Fork 与并发 Run 的安全论证也要重做。现有替代物足够——hook 自身的构造函数做初始化，需要引擎能力时用 `core.AgentFromContext` 在运行期自举。
